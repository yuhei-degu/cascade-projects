# Lunaria Canonical Spec

Last updated: 2026-05-20
Owner: Human final decision, Codex implementation steward
Status: Active source of truth for AI-assisted development

## 1. Product Identity

Lunaria is not only an AI diary app. The first public shape is a Japanese-first AI companion diary, but the internal design should grow toward an AI companion life-log OS.

The emotional promise is simple:

- The user can return every day and feel that Luna remembers the shape of their life.
- The app should be fun, a little playful, and emotionally safe.
- Conversation, diary, memory, games, gacha, and character presentation must reinforce each other without being mixed into one fragile blob.

## 2. Core Pillars

| Pillar | Purpose | Current priority |
|---|---|---|
| Conversation | Daily companion experience, planning, emotional support, playful banter | Highest |
| Diary | Turn daily conversation and events into readable life records | High |
| Memory | Preserve stable facts, values, goals, patterns, and relationship context | High |
| Games | Make the relationship feel alive through small emotional experiences | High |
| Gacha / Items | Reward loop and mood/identity expression, not pay-to-win pressure | Medium |
| Character Presentation | Portrait, expression, motion, outfits, and future Live2D | Medium |
| Life Events | Future bridge for calendar, health, AI glasses, and external inputs | Later foundation |
| Tools / Subscriptions | Track monthly tools, AI usage budgets, renewals, and practical routing advice | Later high-value |

## 3. Non-Negotiable Architecture Rules

Do not merge these concepts into one field or one prompt-only behavior:

- Assistant reply text
- Diary entry
- Core memory
- Memory candidate
- Life event
- Gacha result
- Character state
- Visual expression / motion

Correct flow:

```text
user input / app event
  -> route-specific processing
  -> assistant reply or game result
  -> optional extraction
  -> diary candidate / memory candidate / life event
  -> user-visible review where needed
  -> character state or UI presentation
```

## 4. Conversation Canon

Luna's core personality:

- Childhood-friend distance, warm but not blindly agreeable.
- Light teasing is allowed, especially when the user asks for it.
- Does not hide behind "I am an AI" language.
- Serious topics should slow down, validate, and suggest one small next step.
- Planning requests should produce a concrete order, not just ask what the user wants.
- Calendar/date answers must use explicit JST date context when available and must correct mistakes cleanly.
- Game/gacha reports should be treated as meaningful experiences inside Lunaria, not generic app events.

Hard avoid:

- Raw JSON leaking to the user.
- Mojibake.
- English fallback copy in normal Japanese conversation.
- Over-asking questions.
- Unsupported assumptions like inventing a workplace/school/family detail.
- Saving transient game/gacha results directly into core memory.

## 5. Memory Canon

Core memories are only for stable, reusable context:

- Long-term interests
- Important goals
- Repeated worries or patterns
- Important relationships
- Communication preferences
- Relationship context with Luna

Do not put these directly into core memory:

- One-off moods
- Single gacha pulls
- UI actions
- Temporary game scores
- Raw diary text
- Profile facts that belong in profile tables

Memory candidates are the safety buffer. Game and diary experiences should become candidates first, then review/approval should decide what becomes durable memory.

## 6. Diary Canon

Diary entries should be user-readable records, not hidden prompt state.

Each diary should keep:

- Date
- Title
- Body
- Summary
- Emotion tags
- Topics
- Source conversation / source event references where available
- Prompt version / generated by
- Edit/delete/regenerate path

Diary-derived memories must go through candidates unless the user explicitly confirms.

## 7. Game Canon

Games exist to make Lunaria feel like a companion, not to become a separate grind app.

Endworld v2 is the current core game direction:

- Short emotional vignette run, around 5 to 8 minutes.
- No hard failure required; endings are emotional aftertaste, not punishment.
- User chooses relation mode: lead, yield, collab, plus witness for Luna-initiated moments.
- Result produces residue, closing line, chat handoff, and optional memory candidate.
- Old `lunaria_endworld_v1` session key must not be revived.

Future game additions should reuse the shared core engine when possible:

- Memory Quest
- Dream Repair
- Seasonal event games
- Diary-linked micro quests

## 8. Gacha / Item Canon

Gacha is a reward and expression layer.

Allowed reward types:

- Outfits
- Accessories
- Backgrounds
- Expressions
- Motions
- Room items
- Special lines / voice hooks
- Diary/game flavor items

Rules:

- Gacha result goes to gacha history and user items.
- It may create a light life event.
- It must not directly create core memory.
- Pity/ceiling design must not destroy the existing rarity balance.

## 9. Character Presentation Canon

Assistant reply should eventually be structured:

```ts
type AssistantReply = {
  message: string
  emotion?: string
  expression?: string
  motion?: string
  voice_tone?: string
  topic_tags?: string[]
  should_create_memory_candidate?: boolean
  should_create_diary_candidate?: boolean
}
```

The UI may use expression/motion tags, but conversation logic must still work without the visual layer.

Development path:

1. Static portrait
2. Expression variants
3. Motion CSS placeholders
4. Outfit/item reflection
5. Live2D or equivalent

## 10. AI Development Collision Policy

To keep Codex and Claude from stepping on each other:

| Lane | Codex owns | Claude owns |
|---|---|---|
| Implementation | Next.js app, API routes, scripts, tests | Only when explicitly assigned |
| DB | Migration candidates, verification scripts, SQL safety review | Design review, content review |
| Copy | Runtime copy integration | Drafts, variations, tone review |
| Docs | Canonical spec, runbook, task queue, metrics | Proposal docs, review docs |
| QA | Build/typecheck/smoke automation | Manual checklist and critique |

No agent should edit a file currently assigned to another lane without writing a handoff note first.

High-collision files:

- `lunaria-app/app/page.tsx`
- `lunaria-app/app/api/chat/route.ts`
- `lunaria-app/lib/prompt.ts`
- `lunaria-app/lib/supabase.ts`
- `lunaria-app/package.json`
- `lunaria-app/supabase/migrations/*`

## 11. Current Automation Standard

Every implementation task should leave behind:

- Changed files list
- Verification commands and results
- Risks / deferred work
- AI_DEV_OS metric row
- Next task suggestion

Minimum checks for app code:

```powershell
npx tsc --noEmit --pretty false
npm run build
npm run endworld:check
npm run games:smoke
npm run conversation:cases
```

Use route-specific smoke commands when relevant.

## 12. Current Product Priority

Near-term goal: make Lunaria feel fun and alive before expanding production risk.

Priority order:

1. Conversation quality and Luna voice
2. Endworld/game emotional loop
3. Diary and memory review safety
4. Gacha/item presentation delight
5. Character portrait/expression polish
6. DB-backed inventory/equip flows
7. Production deployment and monetization

## 13. Human Decisions Needed Later

- Whether weekly Endworld should be strict lockout, soft recommendation, or ticket cost.
- Whether game-derived memory candidates should use source_type `game` permanently.
- Which Luna visual style becomes canonical.
- What memory types require explicit user confirmation.
- When production deployment becomes worth the risk/cost.

## 14. Tools / Subscription Usage Candidate

Lunaria may later help the user track subscriptions and AI usage budgets.

Canonical rules:

- Start manual-only; do not connect provider accounts in the first version.
- Do not store passwords, secret keys, or raw provider account payloads.
- Treat costs, subscription status, and AI usage as private user data.
- Do not turn subscription records into core memory automatically.
- If a cost/usage insight matters long-term, make it a memory candidate first.
- Luna's framing should be companion-like: "which tools are helping you this month?" not "you are wasting money."
- Exact provider limits must come from user-provided data or verified official/imported data, not guesses.
