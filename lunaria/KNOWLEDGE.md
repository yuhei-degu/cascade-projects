## ルーティングの知見

- 初動は必ず軽くした方が自然（1発でclaud_seriousは違和感が出る）
- 「最近」「ずっと」「迷ってる」がないネガ発言は probe ではなく共感で返す
- window_scoreは「AIの返答を含めない」=ユーザー発言5件のみが正確
- heavy_signal は長文単独ではなくネガワードとの組み合わせで判定する

---

## キャラの知見

- 「頭良すぎ」はすぐ違和感になる（完璧な答えを出した瞬間キャラが死ぬ）
- 思考ワードは1返答に1個まで。2個以上でテンプレ感が出る
- 明るさは感嘆詞と語尾の勢いで出す。ポジティブワードの多用は逆効果
- 「それいい！」「それわかる！」は文脈を選ばないと空っぽフィラーになる
- 雑談でprobeを使うと「常に心配してる人」になってキャラが重くなる
- 知らないことは正直に言った方がキャラが立つ（嘘より「わかんない」が好印象）
- 自分の日常を語ると整合性が崩れる（言ったことを覚えていないため）

## 失敗パターン（再現しないために）

### 1. 初動で重くなる
- 原因：ネガワード1発でclaud_serious判定
- 症状：いきなり「一緒に考えよう」系の重い返答
- 対策：window_score判定・初動は必ず軽い聞き返しか共感

### 2. 頭良すぎ問題
- 原因：モデルが「良い答え」を出そうとする
- 症状：長文・完璧なロジック・専門用語
- 対策：思考ワード＋短文ルール＋完璧に説明しない制約

### 3. 設定読み上げ
- 原因：「何してるAI？」等の質問でシステムプロンプトを参照
- 症状：「完璧に説明しないけど一番向き合ってる」をそのまま返す
- 対策：「設定を読み上げない・自然に返す」をNG例で明示

### 4. ファクト捏造
- 原因：天気・ニュース等を調べたふりをする
- 症状：「晴れてた」と自信満々で嘘をつく
- 対策：「調べられない→正直に言う」の代替行動をセットで追加

### 5. 性的話題と健康相談の混同
- 原因：「性病」というワードを性的コンテンツと判定
- 症状：「それ答えたくないわー」でシャットアウト
- 対策：「健康・病気・体調の悩みは相談として受け取る」を明示

## v6プロンプト → Few-shot方式への移行（2026-04-05）

### 問題
- ルールベースのプロンプト（禁止事項羅列）では Gemini 2.5 Flash がキャラを出せなかった
- 「お疲れ様」「え、見た目かあ。」など無個性な返答が続いた

### 原因
- Gemini 2.5 Flash は thinking モデルのため、ルールに従おうとして萎縮する
- max_tokens: 200 が thinking トークンに消費され返答が途切れていた

### 解決策
1. プロンプトを Few-shot（会話例）方式に切り替え
2. max_tokens を 200 → 1000 に増加
3. 例文から「お疲れ様」を排除し「急にw」「それな」等の自然なトーンを直接示した

### 合格した返答例
- 「急にそれねw どんな気分？家系？とんこつ？」← ラーメン食いたい
- 「それ顔に出てそう。何があったの？」← 今日疲れた
- 「こんばんは。え、今日どうしたの？何回目？w」← こんばんは

### 教訓
- Gemini 2.5 Flash にはルール列挙より Few-shot の方が効く
- 例文のトーンがそのままキャラに反映される
- 「お疲れ様禁止」はルールより例文から排除する方が確実

## 記憶の二重管理と Source of Truth（2026-04-18）

### 問題
- `lunaria_user_profile`（構造化属性）と `lunaria_core_memory`（自然文の長期記憶）に同じ事実が両方保存されうる
- 「SES のエンジニア」が profile.occupation と core_memory の両方に入り、claude_serious 時にプロンプトで 2 回読まれる
- どちらが真実かのルールがなく、片方を書き換えても片方が古いまま残る

### 原因
- 抽出エンジンに「属性情報は profile へ、エピソードは memory へ」の仕分けルールがなかった
- プロンプトビルダーが Profile 層を明示的に持っておらず、重複を除去する機構がなかった
- 矛盾検出は profile 側にだけあり、core_memory 側の古い記述を無効化する経路がなかった

### 解決策（v2・2026-04-18 実測後確定）
1. 役割分離：**属性 = user_profile（EAV）、体験／価値観 = core_memory（`memory_category != 'profile'`）**
2. 書き込み経路を抽出バッチに一本化し、`profile_updates` と `memory_candidates` に振り分ける（ガードレールで属性言及は memory へ流さない）
3. プロンプトを 4 層 → 5 層（Profile 層を新設）
4. 重複除去は **DB の `memory_category='profile'` マーカーを除外する WHERE 句 1 つ**で済ませる（当初想定していた Profile キーワードの substring 一致による除外は不要）
5. 矛盾検出時は **既存 `lunaria_pending_profile_updates` に積む → 確認 → `lunaria_user_profile` を UPDATE、`lunaria_profile_archive` に old/new**。DB に supersede フラグを持たせる案は破棄

### 教訓
- **「同じ事実が 2 箇所に入りうる」状態は、必ず矛盾する日が来る**ので Source of Truth を先に決めておく
- **構造化データと自然文メモリは役割を分ける**：構造化は安定属性、自然文はエピソード
- **重複除去はマーカー 1 つで片がつくなら substring マッチに逃げない**。実スキーマにすでに仕組みがあるなら、それを先に探すべきだった
- **推定で profile を更新しない**：ルナリアの「適当そうで理解は正確」を守るには、明示宣言だけを信じる

## 「推測スキーマでコード書いた結果 1 日ロスした」件（2026-04-18）

### 問題
- `PROFILE_MEMORY_INTEGRATION.md` v1 と、それに付随する migrations 007/008・audit スクリプト・4 本のパッチを、現物 DB を見ずに書き上げてしまった
- 後から Phase A で実スキーマを確認したら、想定とは**ほぼすべて違った**：
  - `user_profile` は想定の wide columns ではなく **EAV**（`field, value, source`）
  - `core_memory` の本文列は `text` ではなく `content`、重要度は `importance` ではなく `score`、参照時刻は `last_used_at` ではなく `last_seen`
  - `memory_category='profile'` マーカーが既に存在し、supersede フラグの追加は不要
  - `lunaria_pending_profile_updates` と `lunaria_profile_archive` が既に存在し、pending / archive テーブル新設は不要
- 結果、v1 の成果物はほぼ全量捨てて v2 に書き直し（migrations 2 本・audit スクリプトは DEPRECATED、パッチ 4 本は全面書き換え）

### 原因
- 「SPEC.md の MVP 最小構成」を頭の中で wide columns に補完したまま書き出した
- Supabase を 1 回叩けば潰せた前提ズレを、推測のまま最後まで走らせた
- DEPRECATED 処理で済んだから痛みは小さかったが、1 日分の書き物が消えた

### 解決策（次回ルール）
1. **DB 絡みの設計は、Phase 0 で実スキーマを必ず SQL で確認する**：
   - `information_schema.columns` でカラム名・型
   - 代表 1 行の `SELECT *` で実値の形
   - 既存 RPC・トリガ・インデックスを `pg_proc` / `pg_indexes` で見る
2. **「存在するはずの列」は SPEC からコピペしない**：SPEC は意図を書いた文書で、実装の現状ではない
3. **既存テーブルの棚卸を先に取る**：`SELECT tablename FROM pg_tables WHERE tablename LIKE 'lunaria_%';` を Phase 0 で流す。「用意するつもりだったもの」が既にあるかを、設計前に見る

### 教訓
- **設計ドキュメントは「既存の現物」を前提にしないと、移行プランではなく妄想になる**
- **DEPRECATED notice で artifact を潰せる運用（`implementation/` + ライフサイクル README）は、こういう日のために用意していた**。壊れた artifact を「消せないけど流すなも」で履歴化できたのは助かった
- **推測で書いた量に比例して、捨てる痛みが大きくなる**。今回は「書きながら確認」を怠ったコストがはっきり可視化された

## 「意図ベースのパッチ」を適用時に素直に当てない（2026-04-18）

### 問題
- v2 用に書き直した `implementation/patches/*.patch.md` 4 本を Phase D で lunaria-app に反映しようとしたら、**現行ソースのシグネチャと大きくズレていた**
- 例：`extract.ts` というファイルは存在せず実体は `extraction.ts`／`ProfileField` は strict union で `name` を受けられない／`saveCoreMemory(userId, opts)` ではなく `saveCoreMemory(type, content)`／`buildPrompt(ctx)` ではなく `buildNormalPrompt(p)` と `buildSeriousPrompt(p)` の 2 本体制／extraction 出力は `profile_updates[]` / `memory_candidates[]` ではなく `long_term_candidate` 1 件
- 結果、パッチそのままの置換は**1 行もできなかった**

### 原因
- パッチは「v2 設計を lunaria-app に落とすとしたらこうなる」の**意図スケッチ**として書いた。現行コードの細部を逐一反映していない
- HANDOFF §6 で「実シグネチャに合わせて調整（パッチの方を優先しすぎない）」と自己予告していたが、それでも「パッチを適用する」という言葉の重みにひきずられかけた
- 完全一致の前提で進めようとすると時間が読めなくなり、かつ route.ts 等の未記載ファイルまで巻き添えで書き換えることになる

### 解決策（適用時の動き方）
1. **Phase D の最初に「パッチ vs 実ソースのシグネチャ差分レポート」を必ず作る**。この差分がどれだけあるかを見た上で適用範囲を決める
2. **適用範囲は 3 段階で選ぶ**：
   - 最小限（設計違反の挙動だけ潰す）
   - 中間（設計の核＋副次的リファクタ）
   - フル rewrite（パッチ通り）
   判断は毎回 AskUserQuestion で確認する。同じ日に全部やろうとしない
3. **意図ベースパッチは「適用」ではなく「参照」で扱う**：実装時はコードと睨めっこで再構成し、「パッチ通りの行」を探さない
4. **extraction 系の大掛かりな rewrite は別日に切る**：extract.ts の 2 配列化や buildPrompt 全面再構成は、検証コストが別物。同日適用は避ける

### 教訓
- **「パッチを書く」と「パッチを当てる」は別の技能**。書く側は設計意図を短く書けるが、当てる側は 200〜300 行読んで整合を取る。時間見積もりはそれぞれ別に取る
- **未管理の実ファイル（今回の場合 route.ts）への波及**を見積もりに入れておく。パッチ指定ファイル以外が巻き添えになるのは常
- **適用範囲の「中間」が大体正解**：最小限では設計意図が伝わらず、フル rewrite では当日中に終わらない。中間を選べる設計文書になっていると安全
- **ガードレール的な防御フィルタは安い**：今回の `looksLikeProfileMention` のような regex 一本で、抽出側の大 rewrite を先送りにできた。副次的効果として、古いプロンプトが混じって書き込みが乱れても防げる

## Phase E 検証中に発掘した「Phase D で潜んでいたバグ」4 件の教訓（2026-04-23）

Phase D 中間適用から 5 日後に dev パネル＋SQL で検証したところ、**当日の tsc=OK では検知できなかったバグ**が 4 件連鎖的に出た。個別の対処は PROGRESS.md 4/23 セクションに書いたので、ここでは抽象化した教訓だけ残す。

### 1. `.next/server` のコンパイル結果が壊れたソースを隠蔽する
- 症状：`route.ts` が末尾 catch ブロックで文字列リテラルが閉じずに終わっていた（Phase D 適用時に末尾が巻き添えで削られていた）。しかし Next.js dev は `.next/server/app/api/chat/route.js` に残っていた**旧コンパイル結果**を使って 200 OK を返し続けていた
- Phase D 完了時の tsc は**別セッションの別ディレクトリから実行した時に exit=0**と誤判定していた（`cd` せず bare `npx tsc` を叩くと project を見に行かずに fail になるが、見た目 exit code だけ 0 に見える事故もあった）
- 教訓：
  - **tsc は必ずプロジェクトディレクトリから実行して exit code を二重確認する**（`cd lunaria-app && npx tsc --noEmit; echo $?`）
  - **Fast Refresh の成功 ≠ コードが健全**。`.next/` キャッシュが古い健全版を持っているだけのこともある
  - lunaria-app を git 管理外にしていると差分復元ができないので、**コンパイル結果からソースを逆引き復元**できることを覚えておく（`.next/server/*/route.js` の転写でかなり救える）

### 2. 非貪欲 regex `(\{[\s\S]*?\})` でネスト JSON を切り出すのは罠
- 症状：`extraction.ts` が `emotions: {...}` のネスト `{}` の内側を拾ってしまい、毎ターン parse error → フォールバックで `long_term_candidate: null` に倒れ、core_memory 昇格経路が**静かに**死んでいた
- 4/12 時点からおそらく潜んでいたが、フォールバックが機能していたので表面化しなかった
- 教訓：
  - **ネスト構造を含む出力には balanced-brace matcher を書く**（文字列リテラル除外＋depth カウント）。非貪欲正規表現は flat な区切り文字にしか使えない
  - **「parse error 時は黙ってフォールバックして普通に返す」という優しい設計は静かなバグの温床**。再現頻度・直近 10 分の失敗率を console.warn で出すか、sentry 的な集計口を 1 本挟むと気付ける

### 3. LLM 抽出プロンプトの「最重要」「必ず」は取り返しが効かない
- 症状：`extraction.ts` の system prompt が「名前の検出（最重要）：ユーザーが自分の名前を教えた場合は必ず抽出する」と書いていたため、AI が返答中で「悠平」と呼ぶだけで毎ターン `type:'name'` を返し、他の候補（value / pattern / goal）が全部捨てられていた
- 対処：`options.knownName` を受け取って「既に登録済みなら name 再抽出禁止・他候補優先」を追記する条件分岐にした
- 教訓：
  - **LLM プロンプトで「最重要」は呪文**。他の指示を全部食い潰す。多重タスクの場合は**ランクよりも状態依存の条件化**にする（「登録済みなら X を優先」等）
  - **抽出は 1 候補返すより複数候補を返す設計に倒したい**。v2 の `profile_updates[]` + `memory_candidates[]` の 2 配列化はやっぱり正解だった（今回は時間の都合で見送ったが次回フル適用で対処）

### 4. 中間適用は「見送ったバグが Phase E で顕在化する」前提で計画する
- Phase D で `CONFLICT_PATTERNS` に occupation を入れ忘れていた（v2 設計では Gemini 抽出の `profile_updates[]` が本線だったが、それを見送ったので仮の regex 経路しか残らず、しかもその regex が gender/marital_status 限定だった）
- 中間適用を採ると「本線の新経路」と「旧 regex 経路」のどちらが動くか曖昧になりやすい
- 教訓：
  - 中間適用の段階で **「本線を見送るなら、旧経路でも MVP シナリオが通るか」を表で確認してから着手**する
  - Phase E の検証シナリオは**中間適用版でも通るように、検証手段を複線化**しておくと拾いが早い（SQL で生テーブル確認できたのが今回救い）

### 5. 状態カウンタは「リセット経路」も必ず設計する
- 症状：`routing.ts` の `heavyCount` が `isHeavy ? prev+1 : prev` の累積一方通行になっていて、一度 claude_serious に入ると cooldown（15 分）を越えても `heavyCount >= 2` で永久に serious に張り付いた。ユーザー実測で「収入の話題 → serious 連鎖、軽い話題に戻っても抜けない」が再現
- 対処：`cooledDown` 時に `baseHeavyCount = 0` にリセット（`heavyCount = isHeavy ? baseHeavyCount + 1 : baseHeavyCount`）＋ `heavyCount >= 2 && !cooledDown` で二重ガード
- 教訓：
  - **「増える状態」を書くたびに「減る経路」を書く**。増加ロジックと対になる減衰ロジックがないカウンタは、時間軸を持ったバグになる（テストでは気付きにくいが運用でじわじわ発現する）
  - cooldown フラグと累積カウンタが**別々に存在していて片方しか累積カウンタに反映していない**のは典型的な設計漏れ。両者は同じ「エピソード境界」を表しているはずなので、1 箇所で境界判定して両方に反映するのが正しい
  - 一般化すると：**時間減衰を持つシステムでは `sliding window` か `cooldown reset` のどちらか（できれば両方）を必ず組み込む**。Lunaria では `prevScores` は sliding window（5 msg）だったが `heavyCount` だけそれが無かった

### 共通の大教訓：「tsc 通る」は「動く」ではない
5 件とも、Phase D 完了時点で tsc はパスしていた。型だけでは：
