## 3. Phase A で判明した実スキーマ（重要・再記録）

新セッションで確認する必要はないが、パッチ適用時に迷ったらここを見る。

### `lunaria_user_profile`（EAV）
```
(id, user_id, field, value, source, created_at, updated_at)
```
- 現状行：`(gender, 男性, setting)` / `(occupation, ITエンジニア・SES, setting)`
- name は未登録 → cleanup SQL で core_memory から移送予定

### `lunaria_core_memory`
```
(id, user_id, type, content, score, hit_count, last_seen, created_at,
 memory_key, memory_category, updated_at)
```
- **本文列は `content`**（`text` ではない）
- **重要度は `score`**（`importance` ではない）
- **参照時刻は `last_seen`**（`last_used_at` ではない）
- `type` 値域：`pattern`(8) / `goal`(1) / `name`(1) / `value`(1)
- `memory_category='profile'` マーカーで profile 相当行を分離できる（2 行該当）

### 既存テーブル（活用）
- `lunaria_pending_profile_updates (id, user_id, field, detected_value, trigger_message, created_at)`
- `lunaria_profile_archive (id, user_id, field, old_value, new_value, archived_at)`
- `lunaria_preferences`（空・今回は未使用）

## 4. 次に実行する手順（新セッションでやること）

### Step 0. mount 確認
新セッションで `ls /sessions/<session-id>/mnt/` を叩いて、**`lunaria` と `lunaria-app` が両方見える**ことを確認。片方しか見えなければ追加 mount が必要。

### Step 1. Phase B：バックアップ
Supabase SQL Editor で以下を実行し、結果を `lunaria-app/backups/2026-04-18-*.json` に保存：

```sql
SELECT json_agg(row_to_json(t)) FROM lunaria_user_profile t;
SELECT json_agg(row_to_json(t)) FROM lunaria_core_memory t;
```

`lunaria-app/backups/` ディレクトリは `.gitignore` 推奨（既に入っていなければ追加）。

### Step 2. Phase C：cleanup SQL 実行
`implementation/scripts/cleanup_profile_duplicates.sql` を Supabase SQL Editor に丸ごと貼って実行。

**期待結果**：
- `lunaria_user_profile` に `field='name', value='悠平'` の行が 1 件追加される
- `lunaria_core_memory` の `memory_category='profile'` 行が 0 件になる（2 行削除）

**事前・事後チェックは SQL 内に DO ブロックで組み込み済み**。想定と違うデータなら自動で `RAISE EXCEPTION` + ロールバックされる。

確認クエリ：
```sql
SELECT field, value, source FROM lunaria_user_profile ORDER BY field;
SELECT count(*) FROM lunaria_core_memory WHERE memory_category = 'profile'; -- → 0
```

### Step 3. Phase D：パッチ 4 本を lunaria-app に実反映

順序厳守：`profile.ts` → `memory.ts` → `prompt-builder.ts` → `extract.ts`。各段階で `npx tsc --noEmit` で型チェック。

各パッチの意図・差分・注意点は `implementation/patches/*.patch.md` を参照。

**特に注意すべき実列名**：
- `content`（NOT `text`）
- `score`（NOT `importance`）
- `last_seen`（NOT `last_used_at`）
- `buildProfileSummary` の戻り値：`{ text }`（v1 の `keywords` は削除済み）
- `pickMemories` の引数：`(userId, limit=1)`（v1 の `profileKeywords` は削除済み）

### Step 4. Phase E：検証シナリオ
`APPLY_CHECKLIST.md` Phase E の表 5 件を dev パネルで通す：

## 6. 既知のリスク・注意

- **`tsc --noEmit` で型エラーが多発する可能性**：パッチは意図ベースで書いたので、実ファイルの既存関数シグネチャと合わない箇所が出る。その場合は実シグネチャに合わせて調整（パッチの方を優先しすぎない）
- **`memory_category` を絶対 `'profile'` で INSERT しない**（`extract.ts` 昇格時）：DB 側で除外される側に行ってしまう
- **Gemini 抽出プロンプトを変えた直後**：旧キー `core_memory_candidates` を一定期間は fallback で受ける（`extract.patch.md` 末尾に記載）
- **`.or()` の PostgREST 構文**：Supabase JS のバージョンで挙動差あり。効かなければクライアント側フィルタで妥協
- **dev user 1 人分**：cleanup SQL は dev 環境前提。本番には流さない
- **source='setting' でフィルタしている**：推定由来行（source != 'setting'）は現状 Profile サマリに出ない設計。将来推定値を使うなら見直す
